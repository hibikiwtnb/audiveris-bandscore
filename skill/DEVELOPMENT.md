# 核心工程原則：一切都應該簡單！簡單！還是簡單！

> # 【最高開發原則】
> # 一切都應該簡單！簡單！還是簡單！
>
> 任何工程開發、腳本編寫與代碼實裝，**必須無條件嚴格遵守以下原則**：
>
> 1. **極度簡約（Keep It Dead Simple）**：
>    能用 50～80 行直截了當解決的問題，**嚴禁**包裝成數百行的複雜抽象。代碼越精簡、分支越少、邏輯越平鋪直敘，維護成本與出錯機率就越低。
> 2. **嚴禁過度工程化（Zero Over-Engineering）**：
>    未經使用者明確要求的功能，**一律禁止擅自實裝**！
>    - **嚴禁私自添加「自動探測」**：禁止在代碼中盲目掃描系統候選目錄、自動遍歷檔案系統找圖片或執行檔。路徑與參數優先由明確的參數、配置文件或環境變數給定。
>    - **嚴禁搞自作聰明的背景黑箱**：禁止在背地裡用 detached 守護進程、未受控的 background daemon 或靜默重試來掩蓋問題。有依賴沒啟動就直接報錯中止，拒絕 silent fallback。
>    - **嚴禁自作主張的「自動猜測／自動修補」**：禁止引入複雜模糊正則去猜測譜面意圖或全自動提取內容。工具的泛用性是靠**通用結構與標準字典**（如內建 GM 音色表），而不是靠充滿邊緣 bug 的猜測算法。
> 3. **顯式直接勝過隱式魔術（Explicit is Better than Complex Magic）**：
>    輸入是甚麼、輸出是甚麼、要調用甚麼命令，全部要透明直白。不要在腳本裡藏一堆「幫使用者做決定」的多餘邏輯。
> 4. **只解決眼前的具體任務**：
>    不要預先為未來「可能」出現的臆想情境寫代碼。每一次敲下的代碼，都必須為當前任務以最直接、最透明、最簡單的形式服務。
> 5. **先想我們要什麼，不要被 Audiveris 原本的代碼牽著走（降維打擊）**：
>    遇到問題，先用人看譜的方式想：要判斷的是什麼、最直接的依據是什麼（例如「哪行是鼓」＝看每一行譜表的數量與位置，管它是不是 TAB），
>    再去找最短的實現路徑。**不要**先讀它的代碼、順著它原本的分類與流程（TAB／非 TAB、哪一輪找哪種譜表……）一路修補下去——那只會在它的框架裡越繞越深。
>    我們的目標優先於它的代碼整合性：它原本的設計擋路時，繞開或另寫一段簡單的判斷，而不是為了跟它的架構「整合得漂亮」去改它一串內部邏輯。
> 6. **文件只寫現在的狀態，不寫變更經過**：
>    說明、規則、用法文件寫「現在是什麼、怎麼用、有什麼限制」。**不要**寫以前怎樣、改了什麼、修了哪個 bug、哪個 commit 加的、「也算在內」「不再需要」這類只有參與過的人才看得懂的對照——讀的人沒有這個上下文，只會混亂。
>    只有本身就是記錄變更的地方（commit 訊息、研究報告、交接文件）才寫經過。
> 7. **自定模板一律用灰階，沒得商量**：自己學的符號模板（`templates/`），學與比對都用原圖灰度，不用二值圖、也不自己切黑白。細節見 `templates/README.md`。
> 8. **節奏優先，不刪音只是盡量做到**：節奏是音樂最根本的要素。每個小節的長度等於拍號（弱起小節除外），每個聲部都一樣，其他一切都要讓路。
>    不刪音（無損）是盡量滿足的目標，不是必須：和小節長度衝突時，讀錯而超出小節線的音照刪。一個聲部讀錯，不能把其他聲部的小節撐長。
> 9. **驗證靠歌曲重跑，不做高成本的額外測試**：修完之後，用重跑出問題的那首歌（或那一頁）來確認，結果就是證據。
>    **不要**為了找原因另外搭一套高成本的測試，例如二分搜尋 commit、反覆編譯不同版本、自己寫的測試台。原因找不到時，記下現象和出問題的頁，交給下一次重跑或使用者決定。

> ## 最高規則：人工審查只聽 merged 的播放
>
> （本 repo 裡的 merged 指 `songs/<輸入 PDF 檔名>.musicxml`。）
>
> 品質的唯一驗收面是 **merged MusicXML 的實際播放**（MuseScore 等）。
> 只要 merged 播放是錯的，其他一切（個別 normalized、工具、報告、DTD 通過、
> 稽核數字）**全部不算數**。「已修正」以使用者聽過 merged 為準。
>
> **聽只有使用者能做。** agent 的工作做到「產生 merged」為止：產生 merged、跑完 Step 5 的自動檢查，
> 把 merged 的路徑交給使用者聽。不要把試聽列成自己的課題，也不要宣稱播放正確；回報寫「merged 已產生，等你試聽」。
>
> 反過來說：**不要用「檔案字面值看起來對」「audit 過了」推論播放對**——
> MuseScore 對 merged 的容錯與顯示規則不同，只有實際播放能當證據。

# 執行

## 長時批次（OMR/轉檔）要 detach，不要卡在單一命令

逐頁 OMR 21 頁要十幾分鐘，超過 agent shell 的單次 timeout。若用 `cmd &` 起背景，命令 EOF 時 harness 可能把整個 process group 殺掉。正確做法：

```bash
setsid longjob.sh </dev/null > run.out 2>&1 &
# 之後用 poll 迴圈等：grep -q DONE run.out; sleep 15
```

並讓 script 自己寫進度到 `run.out`。不要把長批次塞進一個會被 timeout 砍掉的同步命令。

## 每個 commit 只做一類事

例如：

- normalize topology
- fix one clef region
- repair tuplets
- fix OVER measures
- rehearsal marks
- barline consistency
- effect words
- playback structure
- regenerate merged
